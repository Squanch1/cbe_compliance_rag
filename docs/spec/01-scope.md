# 01 范围边界

## 0. 文档效力

本文件是项目的**强制边界约束**，效力高于其他所有文档与口头讨论。

- 本文件未列入「首期范围」的能力，一律不得实现
- 本文件列入「明确不做」的事项，即使实现成本很低也不得顺手实现
- 需要突破边界时，走第 4 节的变更流程，不得在实现过程中夹带

## 1. 首期范围

### 1.1 已确认

| 维度 | 范围 |
|---|---|
| 目标用户 | 跨境电商卖家（见 `00-overview.md` 第 3 节） |
| 平台 | Amazon |
| 地区与税种 | 欧盟增值税（VAT）、进口一站式服务（IOSS）、一站式服务（OSS） |
| 语料来源 | Amazon 政策页、欧盟官方指南与法规说明 |
| 语料格式 | 超文本标记语言（HyperText Markup Language, HTML）与便携文档格式（Portable Document Format, PDF）混合 |
| 交互形态 | 多轮对话，支持按国家、文档类型、发布机构筛选 |
| 交付形态 | FastAPI 服务层 + Streamlit 演示界面 |
| 嵌入模型 | bge-m3，进程内加载，fp16，稠密 1024 维 + 稀疏双路输出 |
| 检索方式 | 稠密与稀疏混合检索，融合结果参与生成 |
| 生成模型 | 阿里云百炼，走 OpenAI 兼容模式，模型名走配置 |

### 1.2 语料规模

首期精选 30 至 50 篇文档，人工挑选并整理入库，用于验证全链路效果。

自动抓取脚本**不在首期范围**。首期采集方式为人工挑选与整理，待全链路跑通并确认效果后，再评估是否引入采集脚本。

## 2. 明确不做

以下三项由用户确认排除，任何情况下不得实现。

### 2.1 不做税务申报与代缴代办

系统只回答「规则是什么」，不提供申报入口、不代办注册、不代缴税款、不推荐代办服务商。

**排除理由**：一旦引入申报代办，系统性质从「信息检索」变为「业务办理」，需要承担完全不同的责任与合规要求。

### 2.2 不出具法律或税务意见

系统的回答定位是「文档检索结果与原文引用」，不是合规结论担保。

**实现要求**：

- 回答不得出现「你应该」「建议你」这类指令性表述
- 回答应表述为「根据某文档某条款，……」
- 界面必须有明确的免责声明：内容仅供参考，不构成法律或税务意见
- 涉及具体业务决策时，回答应引导用户咨询专业顾问

### 2.3 不做精确税额计算

系统只引用原文中的税率与计算公式，**不替用户计算具体金额**。

不回答的问题示例：

- 「我卖 100 欧元的货到德国，要交多少 VAT？」（需要知道商品分类、申报价值、适用税率，且计算逻辑不在语料中）
- 「我一年要交多少税？」

**排除理由**：税额计算强依赖商品归类、申报价值认定、进项抵扣等大量系统不具备的输入，任何计算都是不负责任的近似。

**实现要求**：识别到计算类提问时，返回第 3.2 节定义的引导式拒答，而不是套用原文公式硬算。

## 3. 灰色地带的判定原则

以下情形不在「明确不做」清单里，但容易滑出边界，统一按本节原则处理。

### 3.1 概念比较类提问

如「IOSS 和 OSS 有什么区别」。

**处理原则**：允许模型归纳差异，但必须同时满足两个条件。

1. **逐条挂载引用**：归纳出的每一条差异，都要能指回支撑它的原文片段（Chunk）。不得出现无引用的对比条目
2. **显式标注来源性质**：回答中必须明确提示「以下对比由系统基于上述原文汇总，原文未直接进行此项对比」，让用户能区分哪些是原文说的、哪些是系统归纳的

若某条差异找不到原文支撑，**只能省略该条目或降级为「无法从现有文档确认」**，不得凭模型自身知识保留。

### 3.2 计算类提问

如「我要交多少钱」。

**处理原则**：走引导式拒答，回复中说明计算需要哪些系统不具备的输入，并引用原文中说明计算方式的条款，让用户自行完成。

### 3.3 超出语料范围的提问

如「TikTok Shop 的规则是什么」。

**处理原则**：明确声明当前语料未覆盖该主题，不得用相近主题的内容替代回答，不得依赖模型自身知识作答。

### 3.4 多份文档规定冲突

**处理原则**：以生效日期最新者为准，并在回答中**显式标注存在冲突以及各自出处**，不得静默选择其中一份。

当冲突文档中有一份或多份未标注生效日期时，上述规则无法适用。此时必须告知用户「存在多份规定，且部分未标注生效日期，无法判断孰新」，**不得默认选一份**。字段定义与入库门禁见 `02-architecture.md` 第 6.2 节。

### 3.5 结论性提问

如「我这样做合规吗」。

**处理原则**：按第 2.2 节处理，只给原文依据，不给合规结论。

## 4. 变更流程

任何突破本节边界的诉求，按以下流程处理：

1. 提出变更，说明动机与不做的后果
2. 写入 `docs/adr/` 下的架构决策记录（Architecture Decision Record, ADR）
3. 由用户确认后，修改本文件相应条目
4. 变更生效后，方可开始实现

**禁止的实现期夹带**：不得以「顺手」「反正很简单」为由，在同一提交中加入本文件未授权的能力。
