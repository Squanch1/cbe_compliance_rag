# 02 分层架构与模块职责

## 0. 本文档的作用

定义系统的分层、模块边界与数据流向。与 `01-scope.md` 的关系：范围边界管「做什么」，本文档管「怎么组织」。冲突时以 `01-scope.md` 为准。

## 1. 架构总览

系统分为两条链路，共用同一套存储与适配层。

```
离线链路（索引构建，人工触发）
  原始文件 ──> 解析 ──> 切分 ──> 向量化 ──> 写入存储

在线链路（问答）
  提问 ──> 检索 ──> 组装上下文 ──> 生成 ──> 引用校验 ──> 回答
```

### 分层视图

```
┌─────────────────────────────────────────────┐
│ 接口层   api/                                │  FastAPI 路由、请求响应模型
├─────────────────────────────────────────────┤
│ 应用层   services/                           │  编排：问答流程、索引构建流程
├─────────────────────────────────────────────┤
│ 领域层   ingestion/ retrieval/ generation/   │  解析、切分、检索、生成
├─────────────────────────────────────────────┤
│ 基础设施 storage/                            │  Milvus/MySQL/MongoDB/Redis 适配器
├─────────────────────────────────────────────┤
│ 配置层   config/                             │  pydantic-settings 统一配置
└─────────────────────────────────────────────┘
        横切关注点  observability/             日志与追踪
```

**依赖方向自上而下，禁止反向依赖，禁止跨层调用。** 领域层不得 import 驱动库，只能通过 `storage/` 暴露的接口访问外部服务。

## 2. 分层职责

### 2.1 接口层 `api/`

- 定义 HTTP 路由与请求响应模型（Pydantic）
- 参数校验、错误码映射、流式响应（Server-Sent Events, SSE）
- **不写业务逻辑**，只做协议转换后调用应用层

### 2.2 应用层 `services/`

- 编排单个完整用例的步骤，是事务与流程的边界
- 首期两个用例：`问答`（query → answer）与 `索引构建`（trigger → indexed）
- 决定「走正常路径还是拒答路径」这类流程判断

### 2.3 领域层

| 模块 | 职责 | 不负责 |
|---|---|---|
| `ingestion/fetcher/` | 读取本地原始文件，登记来源与采集时间 | 网络抓取（见 `01-scope.md` 1.2） |
| `ingestion/parser/` | HTML 与 PDF 解析为统一中间表示 | 切分、向量化 |
| `ingestion/chunker/` | 中间表示切分为父子两级块 | 解析、存储 |
| `retrieval/` | 查询处理、稠密与稀疏双路召回、元数据过滤、融合与精排 | 生成回答 |
| `generation/` | 提示词组装、调用大语言模型、引用校验 | 检索 |

### 2.4 基础设施层 `storage/`

每个外部服务一个适配器，对外暴露领域接口，对内封装驱动。

| 适配器 | 封装 |
|---|---|
| `milvus_store.py` | 向量集合的创建、写入、检索、删除 |
| `mysql_store.py` | 文档元数据、维度表、评测集的读写 |
| `mongo_store.py` | 原始解析产物的读写 |
| `redis_store.py` | 查询缓存、会话上下文 |
| `embedding.py` | bge-m3 进程内加载，稠密与稀疏双路向量化。`health_check()` 检查模型是否已加载 |
| `bailian_client.py` | 大语言模型调用 |

**每个适配器必须提供 `health_check()`**，供连通性脚本与健康检查接口调用。

### 2.5 配置层 `config/`

- 唯一配置入口，用 `pydantic-settings` 的 `Settings` 类
- 启动时校验，缺失必填项直接失败，不静默降级
- 所有密钥只从环境变量读取

## 4. 两条核心数据流

### 4.1 离线链路

```
1. fetcher       读取 data/raw/ 下的原始文件，登记 source_url 与 collected_date
2. parser        按 MIME 类型分派 HTML/PDF 解析器，产出 ParsedDocument
3. mongo_store   写入原始解析产物（保留结构，便于回溯解析质量）
4. mysql_store   写入文档元数据行，取得 doc_id，按元数据齐备情况设置 status
5. services      门禁：status 非 ready 的文档在此终止，不进入向量库（见 6.2）
6. chunker       ParsedDocument 切分为父块与子块两级，子块携带 parent_id 与段落定位
7. embedding     批量向量化，一次调用同时产出稠密与稀疏两路
8. milvus_store  写入稠密向量、稀疏向量与检索用标量字段
9. mysql_store   更新文档状态为 indexed
```

**幂等性要求**：以 `doc_id` 为准，重建同一文档时先删后写，不产生重复向量。

### 4.2 在线链路

```
1. api            接收提问与筛选条件，生成 trace_id
2. redis_store    取会话上下文（多轮）
3. retrieval      查询处理 -> 双路向量化 -> Milvus 混合检索（稠密与稀疏双路召回，RRF 融合，含标量过滤）
4. retrieval      按 parent_id 折叠：同一父块命中多个子块时只保留分数最高者
5. mysql_store    按 parent_id 批量取回父块全文，按 doc_id 批量取回引用元数据
6. services       判断检索质量：低于阈值直接走拒答路径，不调用大语言模型
7. generation     组装提示词（父块全文 + 引用元数据 + 拒答约束）
8. bailian_client 调用大语言模型
9. generation     引用校验：每条结论是否挂载引用，无引用则降级为声明依据不足
10. redis_store   写回会话上下文与查询缓存
11. api           返回答案与引用列表，每条引用含子块原文与 parent_id，父块全文不随本次响应返回
```

**关键点**：第 6 步的拒答判断发生在生成之前。这是架构层面的把控，不依赖提示词说服模型。

## 5. 存储分工

### 5.1 各存储承担什么

| 存储 | 存什么 | 为什么是它 |
|---|---|---|
| Milvus | 子块稠密向量、稀疏向量 + 过滤与定位标量字段 | 唯一能同时承载稠密与稀疏两路向量检索并完成结果融合的组件 |
| MySQL | 文档元数据、父子分块表、平台/国家/文档类型维度表、评测集 | 需要事务、唯一约束与关联查询；分块表自引用，靠 JOIN 取父块正文 |
| MongoDB | 原始解析产物、中间表示 | 不同来源的 HTML/PDF 结构差异大，字段不固定，关系型表结构难以容纳 |
| Redis | 会话上下文、查询缓存 | 键值读写、带过期时间，适合高频短生命周期数据 |

### 5.2 一个必须说清的取舍：标量字段冗余

检索要按国家、文档类型、发布机构过滤，**这些过滤必须发生在 Milvus 内部**。若先查 MySQL 拿到 doc_id 列表再回 Milvus 过滤，等于把检索退化成暴力扫描，失去向量库的意义。

因此 Milvus 中**冗余存一份「过滤与定位」标量字段，且仅限这一份**。其余只用于展示的字段不进 Milvus，检索后按 `doc_id` 批量回查 MySQL。

**判据**：一个字段是否进 Milvus，取决于它是否参与过滤或定位。

| 进 Milvus | 不进 Milvus（检索后回查 MySQL） |
|---|---|
| `chunk_id`（主键，定位与删除） | `source_url` |
| `doc_id`、`chunk_index`（定位） | `effective_date`、`collected_date` |
| `country`、`doc_type`、`publisher`（过滤维度） | 文档标题 |
| `parent_id`（不可变指针，见下） | 父块与子块正文 |

**`parent_id` 是唯一不参与过滤却仍进 Milvus 的字段。** 它的作用是支持召回后立即按父块折叠：同一父块下的多个子块常常同时命中，若不折叠就会返回多条高度重复的上下文，既浪费 token 又干扰生成。折叠动作发生在 Milvus 召回之后、回查 MySQL 之前；若 `parent_id` 不在 Milvus 里，就必须先回查一次才能去重。该字段不可变且体积极小，不引入双写一致性问题。

**收益**：`source_url` 与标题这类会变动的字段，全系统只有一份，不存在双写不一致。回查是**一次** `WHERE doc_id IN (...)` 批量查询，N 条引用只增加一次数据库往返，成本可忽略。

**代价与兜底**：过滤维度字段仍有冗余。**MySQL 为唯一事实来源（Single Source of Truth）**，Milvus 中的标量字段视为可随时重建的派生数据；二者不一致时以 MySQL 为准，靠重建索引修复，不做分布式事务。由于国家、文档类型、发布机构均属低频变动字段，实际出现不一致的概率很低。

### 5.3 分阶段接入

四个存储不是同时接入的。

| 阶段 | 接入 | 理由 |
|---|---|---|
| M1 | Milvus + MySQL + Redis | Milvus 与 MySQL 是主链路的最小集合；Redis 承载多轮对话的会话上下文与查询缓存。问答流程从一开始就按多轮设计，后补会话存储会导致流程返工 |
| M2 | 加 MongoDB | 存原始解析产物，服务于解析质量回溯与调试。M1 阶段原始文件保留在 `data/raw/` 即可 |

**MongoDB 是四者中最不紧急的**，不因为「反正有服务」就提前接入。

## 6. 关键设计决策

### 6.1 统一中间表示

HTML 与 PDF 解析后产出同一种结构 `ParsedDocument`，下游的切分、索引、检索完全不感知原始格式。

**收益**：新增文档格式只改 `parser/`，不动下游。
**代价**：多一层数据模型；PDF 的表格与双栏排版在转换中会损失部分信息，需在 `ParsedDocument` 中保留原始文本块以兜底。

### 6.2 引用溯源的信息设计

「可追溯」是项目的核心主张，落实为数据结构约束。每个检索单元携带：

| 字段 | 用途 | 存放位置 | 来源 | 缺失时 |
|---|---|---|---|---|
| `chunk_id` | 检索单元主键 | Milvus + MySQL | 切分程序生成 | 不可能缺失 |
| `doc_id` | 关联文档元数据 | Milvus + MySQL | 索引程序生成 | 不可能缺失 |
| `chunk_index` | 文档内定位 | Milvus + MySQL | 切分程序生成 | 不可能缺失 |
| `parent_id` | 指向所属父块 | Milvus + MySQL | 切分程序生成 | 不可能缺失 |
| `country`、`doc_type`、`publisher` | 检索过滤维度 | Milvus + MySQL | 人工登记 | **阻止进入向量库** |
| `source_url` | 回溯原文 | MySQL | 采集时登记 | **阻止进入向量库** |
| `effective_date` | 判断时效（见 `01-scope.md` 3.4） | MySQL | 解析抽取或人工确认 | 允许为空，回答中必须标注 |
| `collected_date` | 判断采集新鲜度 | MySQL | 系统时间，自动 | 不可能缺失 |

存放位置的划分依据见 5.2：参与过滤或定位的字段进 Milvus，纯展示字段回查 MySQL。

#### 6.2.1 两层门禁

不采用「字段不全就丢弃」的一刀切，改为文档状态机：

```
MySQL   文档记录可存在，status = pending，并记录缺失字段清单
          |
          | 补齐必填元数据
          v
MySQL   status = ready
          |
          | 索引流程
          v
Milvus  只接收 status = ready 的文档切片
```

**必填元数据指 `source_url` 与三个过滤维度（`country`、`doc_type`、`publisher`）。** 任一缺失，该文档的切片不进入向量库，因此永远不会被检索到、不会被引用。但文档记录本身保留在 MySQL 中，可随时查询「还差哪些文档没补齐」，不会静默丢数据。

#### 6.2.2 effective_date 为空的处理

`effective_date` 为空**不阻止入库**，但有两个强制要求：

1. 该字段在 Milvus 中以空值存储，检索时能被识别
2. 生成的回答引用到这类文档时，**必须显示「未标注生效日期」**，不得静默省略，更不得推断一个日期填上

#### 6.2.3 与时效冲突处理的关系

`01-scope.md` 第 3.4 节要求多份文档规定冲突时以生效日期最新者为准。当相关文档的 `effective_date` 为空时该规则无法适用，此时必须显式告知用户「存在多份规定，且部分未标注生效日期，无法判断孰新」，**不得默认选一份**。

### 6.3 拒答是一等公民

拒答路径与正常生成路径在架构上平级，有独立的返回结构与测试用例，不是提示词里的一句嘱咐。

触发条件至少两条：

1. 稠密检索的最高余弦相似度低于配置阈值。判据为何不用融合分数，见 `03-data-model.md` 2.5
2. 大语言模型返回的结论无法匹配到任何引用片段

### 6.4 可替换点

以下三项在首期未定或未启用，通过抽象接口预留，**不得让具体实现渗透到领域层**：

| 待定项 | 抽象接口 | 当前处理 |
|---|---|---|
| 百炼具体模型 | `LLMProvider` | 模型名走配置项 |
| 嵌入模型替换 | `EmbeddingProvider` | 首期固定 bge-m3，接口层不暴露 `milvus_model` 与 `FlagEmbedding` 的类型 |
| 是否引入精排 | `Reranker` | 定义为可空接口，M1 阶段传入空实现 |
| 未来扩充平台与税种 | 维度表 + 标量字段 | 加数据不改架构（见 `01-scope.md`） |

### 6.5 父子分块与检索上下文

采用父子分块（Parent-Child Chunking，又称 Small-to-Big Retrieval）：**用子块做向量检索，把父块喂给大语言模型。**

**动机**：检索精度与上下文完整性是一对矛盾。块切得小，向量语义聚焦、匹配更准，但单块信息不足；块切得大，上下文完整，但向量被稀释、匹配变差。父子分块把这对矛盾拆到两个阶段各自优化。

**切分粒度**（首期配置，跑通后依评测结果调整）：

| 层级 | 目标长度 | 作用 |
|---|---|---|
| 父块 | 约 1500 token | 进入提示词的上下文单位 |
| 子块 | 约 300 token | 建立向量索引与执行检索的单元 |

**只有子块建立向量索引**，父块不嵌入。父块的作用是承载上下文，不需要被检索到。

**检索时的折叠**：同一父块下可能有多个子块同时命中，召回后按 `parent_id` 折叠，每个父块只保留分数最高的子块作为代表。折叠必须在回查 MySQL 之前完成，因此 `parent_id` 需存在于 Milvus（见 5.2）。

**引用的定位**：引用锚定到**子块**（精确到段落），响应中携带子块原文与 `parent_id`。父块全文**不随问答响应返回**，由界面在「展开上下文」时调用独立接口按 `parent_id` 拉取。这样用户既能看到支撑结论的确切文字，也能按需看到完整语境。

**父块懒加载的理由**：父块约 1500 token，折合三千至五千汉字。若 5 条引用都随响应携带父块，响应体将达两万字量级，而多数情况下用户不会展开查看。改为按需拉取后，问答接口的响应体积与首屏延迟不因是否使用父子分块而变差。代价是多一个接口，契约见 `04-api-contract.md`。

### 6.6 混合检索

采用稠密与稀疏双路召回，再融合排序。

| 路 | 向量来源 | 擅长匹配 |
|---|---|---|
| 稠密 | bge-m3 的稠密输出，1024 维 | 语义相近但用词不同的表述 |
| 稀疏 | bge-m3 的稀疏输出，模型学得的词汇权重 | 专有名词与精确术语（IOSS、OSS、150 欧元阈值） |

**稀疏这一路解决什么问题**：跨境电商从业者提问时会直接使用英文缩写——「IOSS 的阈值是多少」「VAT 号怎么办」。这类词元在稠密空间里信号很弱（罕见、语义孤立），但恰恰是判断相关性的决定性线索。稀疏路按词元权重精确匹配，正好补上这个短板。

**关于跨语言的边界**：稀疏匹配依赖**词元重合**。中文字符与英文单词是不同的词元，因此纯中文表述与英文原文之间没有稀疏匹配，跨语言的语义对应**完全由稠密路承担**。稀疏路只在共享词元上生效——拉丁字母缩写（IOSS、OSS、VAT）与数字（150）恰好属于这一类，这正是本场景下混合检索仍然有效的原因。

**两路向量一次产出**：由同一次模型调用生成，不存在两路使用不同文本或不同切分导致的错位。

**融合方式采用加权求和**（Milvus 的 `WeightedRanker`）。两路分数的量纲由 Milvus 内部归一化处理，无需自行处理。选加权求和而非倒数排名融合（Reciprocal Rank Fusion, RRF）的理由：

1. **权重可解释**——「语义占七成、词元匹配占三成」这样的表述能直接写进文档、也能向他人解释；RRF 的排名机制无法表达这种偏好
2. **保留分差信息**——RRF 只看排名，两路各自第 1 名与第 2 名之间无论差距多大都被视为只差一位；加权求和保留了分数差距
3. **可随查询调整**——若后续发现含英文缩写的查询需要提高稀疏权重，加权求和允许按查询特征动态调权，RRF 做不到

**代价**：权重需要标定，是多出来的超参。首期取值在评测集上比较后写入配置，不凭直觉设定。更换嵌入模型或语料构成后需要重新标定。

**精度约束**：模型固定 fp16。fp16 与 fp32 产出的向量存在差异，**建索引与查询必须使用同一精度**，切换精度等同于重建索引。

**标量过滤同时作用于两路**：`country`、`doc_type`、`publisher` 的过滤条件附加在两路召回请求上，不因混合检索而失效。

## 7. 模块依赖规则

强制约束，代码评审时逐条核对：

1. `api/` 只能依赖 `services/` 与 `config/`
2. `services/` 可以依赖所有领域层模块与 `config/`
3. 领域层模块之间**只允许单向依赖**：`ingestion → indexing → retrieval → generation`
4. 任何模块不得直接 import `pymilvus`、`pymysql`、`pymongo`、`redis`、`openai` 等驱动，一律经 `storage/`
5. `observability/` 可被任意层依赖；它不反向依赖任何层

## 8. 错误处理与超时

- 所有网络调用必须设置超时，禁止无限等待。超时值走配置项
- 外部服务不可用时**快速失败并返回明确错误**，不重试到耗尽用户耐心
- 检索或生成失败时，返回结构化的错误响应，不得返回空答案冒充正常结果
- 每个请求携带 `trace_id`，贯穿日志，便于定位

## 9. 明确不做

以下为架构层面的排除项，与 `01-scope.md` 第 2 节对应：

- 不做分布式事务，多存储一致性靠重建兜底
- 不做消息队列与异步任务调度，索引构建为同步的人工触发流程
- 不做多租户与权限模型
- 不做自动化的文档增量更新
