## 1. small caps 被拆成多段：一个被实测推翻的假设

### 现象

从欧盟 PDF 提取出的文本里出现 `I MPORT S CHEME`，而原文是 `IMPORT SCHEME`。

### 根因

PDF 用**字体切换**实现小型大写（small caps）：首字母用全尺寸 12pt，其余字母用 9.5pt 但显示为大写。PyMuPDF 因此把 `IMPORT` 拆成两个 span：

```
TimesNewRomanPSMT  12.0pt  'I'
TimesNewRomanPSMT   9.5pt  'MPORT '
```

**字体名完全相同**，靠字体名区分不了。

### 候选方案

| 方案 | 思路 |
|---|---|
| A | 按 bbox 坐标算相邻 span 的间距，间距接近 0 就不加空格 |
| B | 直接拼接 span 文本，不加任何分隔符 |

方案 A 是我最初的设想，甚至准备写一套「单个大写字母 + 紧跟更小字号则合并」的规则。

### 最终选择

**方案 B：直接拼接。**

### 为什么

**先跑了真实数据，方案 A 的假设被推翻。**

```
直接拼接                                | 加分隔符
'following customers:'                 | 'following customers :'
'...with Article 39 as from...'        | '...with Arti cle 39 as from...'   ← 单词被切断
'ViDA [TOPIC 8]'                       | 'ViDA [ TOPIC 8 ]'
```

两个发现：

1. **PyMuPDF 的 span 文本自带必要的空格**——`'MPORT '` 带尾随空格，所以直接拼接就能得到 `IMPORT SCHEME`，方案 A 完全不必要
2. **加分隔符反而有害**——PyMuPDF 有时把一个完整单词拆成多个 span，插分隔符会把 `Article` 切成 `Arti cle`

### 教训

**如果没先验证就按原设计写，会产出 20 行复杂规则，它不仅没必要，还会引入新 bug。**

验证成本 5 分钟；不验证的成本是一整套白写的逻辑，以及一个更隐蔽的文本损坏问题。

实现见 `pdf_parser._join_spans()`。

## 2. 页码剔除：组合条件比单一条件可靠

### 现象

欧盟 PDF 每页底部有页码 `5/105`，需要剔除。但**每页的页码文本都不同**，所以不能用「重复出现的文本」识别。

### 候选方案

| 方案 | 单独使用的结果 |
|---|---|
| A. 按位置（页面底部区域） | **实测失败**——正文会延伸到页面底部，第 41 页的正文一直到 y=782（页高 842） |
| B. 按文本模式（`^\d+/\d+$`） | 正文里出现 `1/2` 这种分数是很正常的 |
| C. **位置 + 文本模式，两者同时满足** | 正确 |

### 最终选择

**方案 C。**

### 为什么

两个条件**各自都不够**，但**交集非常精确**：一行同时满足「是 `数字/数字` 格式」且「落在页面底部 10%」的概率极低。

实现：

```python
def _is_page_number(text: str, top: float, page_height: float) -> bool:
    if top < page_height * _BOTTOM_ZONE_RATIO:   # 0.9
        return False
    return bool(_PAGE_NUMBER_PATTERN.match(text))
```

### 边界用测试锁住了

- 底部但非页码格式的文本 → **保留**（第二条件不满足）
- 非底部但是页码格式的文本 → **保留**（第一条件不满足）

两条测试都在 `tests/unit/test_pdf_parser.py::TestPageNumberRemoval`。

## 3. 正文在哪：通用启发式不敌站点专用选择器

### 现象

Amazon 帮助页保存下来有 191KB，但去标签后正文只有 2736 字符，其余全是导航、页脚、语言选择器、反馈表单。

### 候选方案实测对比

| 方案 | 结果 |
|---|---|
| A. 只取站点配置的容器 `#help-content` | **7 个标题（全是问题）+ 15 个段落，干净** |
| B. 排除 `header`/`footer`/`nav`/`aside` 等语义标签 | 残留三个噪声：语言选择器、相关文章、需要更多帮助 |
| C. 按「文本密度」自动找主容器 | 未实现，评估后认为不如 A 可靠 |

### 最终选择

**方案 A：站点选择器表，未配置的站点直接报错。**

```python
SITE_CONTENT_SELECTORS = {
    "sellercentral.amazon.com": "#help-content",
}
```

### 为什么

- 方案 B 看起来更通用，但**实测在那份页面上无效**——噪声根本不在语义标签里
- 方案 C 是在猜「哪个容器文本最密」，而该页面有明确的容器 id，没有猜的必要
- **未配置时直接报错**，而不是退回通用规则产出脏数据

报错的价值在于：**它会逼着你先打开真实页面看 DOM**，而这恰恰是正确的接入流程。脏数据不会报错——你不会发现「正文里混进了语言选择器」，直到检索结果变得奇怪。

### 代价（明知的取舍）

选择器是站点专用的，接入新来源要配置。首期语料来源集中（Amazon + 欧盟官方），这个代价可以接受。

实现见 `html_parser.SITE_CONTENT_SELECTORS` 与 `content_selector_for()`。

## 4. 标题层级：用相对关系，不写死数值

### 问题

HTML 有 `<h1>`~`<h6>` 直接标明层级，**PDF 什么都没有**——只能靠字号推断。

### 候选方案

| 方案 | 问题 |
|---|---|
| A. 写死阈值，如「大于 12pt 就是标题」 | 换一份正文 14pt 的文档就全错 |
| B. **字号相对关系**：最大的是 1 级，次大的是 2 级…… | 自适应任何排版 |

### 最终选择

**方案 B。**

```python
body = body_font_size(lines)
larger = sorted({round(l.size, 1) for line in lines if line.size > body}, reverse=True)
return {size: index + 1 for index, size in enumerate(larger)}
```

### 实测验证

两份欧盟 PDF（99 页与 105 页）映射**完全相同**：

```
{22pt: 1, 18pt: 2, 16pt: 3, 14pt: 4, 13pt: 5}    正文 12pt
```

| 层级 | 字号 | 实际是什么 |
|---|---|---|
| 1 | 22pt | 封面主标题 |
| 2 | 18pt | 封面副标题与法规列表 |
| 3 | 16pt | `Contents` / `List of figures` |
| 4 | 14pt | 一级章节（36 行） |
| 5 | 13pt | 二级章节（46 行） |

### 一个被排除的候选

**11pt 不是标题。** 它有 727 行，一度怀疑是噪声。查证后发现是**免责声明、前言这类次级正文**——是**有用的内容**，既不该当标题，也不该剔除。

## 5. 段落边界：阈值从数据分布里定，不是猜的

### 问题

PDF 里每一行都是独立对象，**没有 `<p>` 标出段落边界**，只能靠行距推断。

### 实测行距分布

```
13.8 pt : 1612 次   ← 正常行距（波动范围 11.5 - 14.5）
25.8 pt :  253 次   ← 段落间距（波动范围 24.6 - 26.4）
```

### 阈值的选择

**取 20pt。** 依据是**两档之间有明显空档**（14.5 → 24.6），阈值落在这个空档里的任何位置都成立，取中间最安全。

```python
_PARAGRAPH_GAP = 20.0
```

这个数字不是调出来的，是**从分布里看出来的**——换个排版要重新看一次分布。

### 跨页的处理

**一律断开，不做续段判断。**

理由是不对称的：判断跨页续段需要额外信息（页脚样式、缩进、句子是否完整），判断错的代价是一段被切成两半；而**误合的代价更大**——把两页无关内容并成一段，对检索的干扰更严重。

### 顺带查清的一件事

分布里有 148 对行间距为 0，一度怀疑是双栏排版。查证后是**目录里的章节号与标题并排**：

```
y=89.4  A: '1'                               ← 章节号
        B: 'KEY ELEMENTS OF THE NEW VAT...'  ← 标题
```

再看第 10 页所有行的左边界 x0 都是 70.8——**确认没有双栏**。处理方式是间距 < 1pt 视为同一行，拼接。

## 6. 平局处理：一个「不确定性」缺陷

### 现象

测试失败：只有「标题 1 行 + 正文 1 行」时，标题被当成了正文，层级推断全错。

### 根因

```python
return Counter(sizes).most_common(1)[0][0]      # 错
```

`most_common` 在**计数相同时按出现顺序任选**。所以结果取决于文档里哪一行排在前。

### 为什么这不是「偶尔出错」

关键区别：

- 「偶尔出错」= 有明确的正确解，某些输入下算错
- **「不确定性」= 没有稳定的行为，同样的数据换个顺序结果就变**

后者更危险，因为**它不会稳定复现**，排查时容易归咎于数据而不是代码。

### 修复

**平局时取较小的字号**——标题总是比正文大，较小的那个更可能是正文。

```python
top_count = max(counts.values())
return min(size for size, count in counts.items() if count == top_count)
```

### 教训

这个缺陷是**测试暴露的**，而这个函数我一度认为「简单到不用测」。

真实文档里正文行数远超标题，平局不会出现——**所以这个 bug 在生产数据上永远不会触发**，但它确实存在。测试造出的极端输入把它逼出来了。

## 7. 目录不剔除：没有验证过的优化不做

### 查证结果

| 项 | 值 |
|---|---|
| 行数 | 93 行 |
| 位置 | 全部集中在第 3-6 页 |
| 特征 | 连续点线（`......`） |
| 字号 | 11pt（73 行）与 12pt（20 行）——**与正文重叠，按字号区分不了** |

### 候选方案

| 方案 | 评价 |
|---|---|
| A. 剔除含点线的行 | 不彻底——目录里不含点线的标题行会残留 |
| B. 识别目录区块整块剔除 | 最干净，但要写一套区块识别规则并测它 |
| C. **先不处理** | ✅ |

### 最终选择

**方案 C。**

### 为什么

- 只占 **2%**（93 / 4393）
- **点线让它的向量相似度天然偏低**，不太会挤进检索结果
- 更重要的是：**现在处理是在猜**

真正的判断依据是「目录有没有实际污染检索结果」，而那要等检索链路跑起来才知道。

**这不是「以后再说」的逃避，而是明确的决策**：把它记为待验证项，有了检索结果回来复核。如果检索结果里出现目录内容，再按方案 B 处理。

## 贯穿始终的三条原则

### 一、先验证，再设计

三个例子：

- small caps：原设计的坐标规则，实测后发现不必要且有害（第 1 节）
- 页码剔除：按位置删的方案，跑了一遍才发现正文会延伸到页底（第 2 节）
- 段落阈值：不是调出来的，是从分布里看出来的（第 5 节）

**代价对比很悬殊**：每次验证 5 分钟，每次返工是重写一套逻辑。

### 二、不确定时宁可报错

- 站点未配置选择器 → 报错（第 3 节）
- 正文容器为空 → 报错，不产出空产物
- PDF 没有文本层（扫描件）→ 报错，不产出空文档
- 路径是相对的 → 报错，**且先判绝对路径再判存在性**（报错原因要说准，否则把排查方向带偏）

**理由一致**：脏数据比报错更难排查。报错告诉你去哪看，脏数据不会。

### 三、相对关系优于写死数值

- 标题层级由字号排序决定，不写死「14pt 是 1 级」（第 4 节）
- 路径由模块位置推算，不依赖工作目录

写死的数值在换一份文档、换一台机器、换一个 IDE 之后就会失效，而且失效方式往往很隐蔽。
