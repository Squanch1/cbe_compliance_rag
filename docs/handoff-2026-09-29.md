## 1. 阈值这件事的语义已经变了

这是最容易搞错、也最重要的一条。

**阈值原本的定位是「判据」**——低于它就算证据不足，程序直接拒答。
**现在的定位是「粗筛」**——低于它只是「连碰都不用碰」，省下一次模型调用；高于它交给模型，由模型判断材料够不够。

分工变成：

| 分数 | 谁来判断 |
|---|---|
| 低于粗筛线 | 程序直接拒答，不调模型（明显无关的问题） |
| 高于粗筛线 | 交给模型，提示词里已要求它材料不足就明说依据不足 |

改语义的原因是实测数据：**稠密相似度分不开「主题相近但没答案」和「有答案」**。所以这条线不能再承担「判断够不够」的职责，它做不到。

代码里已经落地的部分：

- `src/cbe_rag/retrieval/service.py` 的 `is_evidence_sufficient` 已重命名为 **`passes_prefilter`**，含义是「值不值得交给模型」。
- 阈值未标定时（配置为 `None`）抛 `UncalibratedThresholdError`，**报错而不是放行**。

## 2. 判据为什么是稠密路最高余弦

用的是 `MilvusStore.top_dense_score()`，**不是两路融合分**。理由写在检索层的注释里：

> 余弦相似度有绝对含义（0.6 就是 0.6），而融合分经过归一化与加权，数值随权重变化——同一份语料在 0.7/0.3 下给 0.6970、0.5/0.5 下给 0.6407，拿它当阈值没有可比性。

排序用融合分，判断够不够用稠密余弦，这两件事分开。阈值是个绝对数值，不该因为调了权重就变。

## 3. 已经否掉的路：别再试一遍

**「改用稀疏路分数当判据」——已否决，理由是错的。**

当时的想法是：该拒答的题用词（关税、商标、品牌备案）语料里根本没有，稀疏路是词元级的，应该更敏感。

**但这个思路有两个致命问题：**

**一、中英跨语言，稀疏路全线趋近 0。** bge-m3 的稀疏向量是词元级的，不做跨语言对齐。语料里欧盟那两份是英文，中文问题走稀疏路，token 根本不是同一批。

**二、一个恒为 0 的指标能「分开」任何两类。** 该答的稀疏分全都很低、该拒的也很低，看起来「该拒的都低」像是分开了，其实两边都低，根本没有区分度。只要把阈值定在 0 和 0 之间就能得到漂亮的「分类准确率」。这是个陷阱。

结论：**在这个场景里只有稠密路在真正工作。**

## 6. 标定目标

**不是「两类判对最多」，而是「在不误伤任何该答的前提下，尽量多拦住明显无关的」。**

约束是硬的，因为两边的代价不对称：

- 漏拦的代价：多调一次模型，花点钱
- 误伤的代价：用户拿不到本来能答的问题

实现见 `scripts/calibrate_threshold.py` 的 `suggest_thresholds(scores, max_missed=0)`。它**返回全部不误伤的候选线**，不只最优那条——因为拦得最多的那条往往贴着该答的最低分，一点余量都没有，只给一条会让人以为它稳当。

## 8. 核对代码时发现的两个问题（已于同日修复）

这两条在本文档写完后当天就修掉了，记录在此供回溯。**新会话不必再处理。**

修完全量测试 954 个通过。

**一、`render()` 里「余量」的正负号是反的。**

`scripts/calibrate_threshold.py` 里：

```python
(item.threshold - lowest_answer)
```

因为粗筛线永远只能定在该答最低分**之下**（定在上面就误伤），这个式子恒为负或零。实测复现（该答 0.8333 / 0.5867，该拒答 0.4877）：

```
线 0.5867　拦住 1 条　余量 0.0000　← 贴着该答的最低分，没有余量
线 0.4877　拦住 0 条　余量 -0.0990
```

而紧跟的说明文字写的是「余量越小，越容易被一道分稍低的该答题目撞上」。按这个说法，**最安全的那条线（0.4877）反而显示成余量最小**，读的人会把危险的当成安全的。

**已改为** `lowest_answer - threshold`：0.5867 给 0.0000，0.4877 给 0.0990。并补了 `TestRenderMargin` 三条测试盯住这个符号——之前这一列没有任何测试覆盖。

**二、`render()` 里有重复的守卫，第二个分支是死代码。**

`scripts/calibrate_threshold.py` 里连着两个 `if not suggestions:`：

```python
if not suggestions:
    lines.append("评测集是空的，没法定阈值。")
    return lines

if not suggestions:                      # 永远不会执行到这里
    lines.append("没有一条线能在不误伤的前提下拦住东西。")
    ...
```

`suggest_thresholds` 只要拿到非空输入就一定会返回至少一条线（分数最低的那个候选，拦住 0 条、误伤 0 条，恒满足 `max_missed=0`），所以 `scores` 非空时 `suggestions` 必非空。第二段提示语永远不会显示。

**已直接删除**该分支（只删不改判据）。所以真遇到「最优线一条都拦不住」（该答分数整体偏低）时，报告会只列一行 `blocked=0` 的线，不额外解释——这点是知情取舍。

流程：

```
用户提问
  ↓
① 拿原问题去 Redis 的问题列表里精确比对
  ├─ 命中 → 直出
  └─ 没命中 ↓

  ├─ 拿到 → 直出
  └─ 没有 → 走 RAG
```

FAQ 是一份**独立的问答表**（MySQL），配 Redis 做精确命中，向量库不参与。

已定的细节：

- **切词用 jieba，不用配缩写词典。** 已实测 jieba 默认把连续英文整段保留，`IOSS` / `VAT` / `OSS` / `EU` / `DE` 都原样成一个 token，IDF 权重正常。

### 13.5 发现语料语言这个问题（2026-09-30）

做 FAQ 术语核对时查出来的：**欧盟那份解释性说明有官方中文版**，但只对应 2020 版；2027 修订版（ViDA）2026 年 7 月底发布，**至今只有英文**。

这一条动摇的东西不少——首期三份语料里两份是英文，而产品是给中文卖家、中文提问的。详见 `docs/adr/0002-corpus-language.md`。要点：

- 今天 2026-09-30，**2020 版才是现行有效的那一版**（生效 2021-07-01），2027 版要到 2027-01-01
- 能换官方中文的，恰好就是现在最有用的那一份
- 英文的好处全在覆盖（时效、原文），坏处全在检索（稀疏路对跨语言空转）——两者不冲突，所以不是二选一
- 若走「2020 换中文」，**ADR 0001 的 1.2 节理由要重写**，那 40 条 FAQ 译文大部分成了重复劳动

**尚未拿到官方中文版原文核对**，下载被本机路径守卫拦住，待人工下载后确认。

**ADR 里修掉了一处流程缺陷。** 早先的草案在第 ③ 步写了「取不到 FAQ 答案 → 走 RAG」的兜底。那是错的：BM25 的候选集就是 FAQ 表的问题集，匹配上了却取不到答案，只能是**该行的答案字段为空**——数据缺陷，不是检索问题。走 RAG 会把它掩盖成一次正常的降级，脏数据永远没人发现。

改后：取不到答案**报错留痕**（`internal_error`），并把门禁前移到入库（问题或答案为空不得入库）和加载（过滤 + 报警）两步。同时明确 Redis 只是问题集的**缓存**，唯一来源是 MySQL，失效一律回源。详见 ADR 的 2.5、2.6、2.7 三节。
