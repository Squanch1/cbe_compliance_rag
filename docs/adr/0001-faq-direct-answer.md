# ADR 0001：FAQ 问答对直出

- **状态**：提议，待确认
- **日期**：2026-09-30
- **相关文档**：`01-scope.md`（需同步修改）、`02-architecture.md`、`03-data-model.md`、`04-api-contract.md`

## 1. 背景与问题

### 1.1 高频问题在重复付费

卖家问的高频问题高度集中——「IOSS 的适用金额上限是多少」「非欧盟卖家能不能注册 IOSS」「亚马逊要求的 60 天期限能不能延长」。这些问题**每次都要走完整链路**：双路编码、混合检索、折叠、恢复父块、组装提示词、调生成模型、校验引用。

同一条问答，答案是固定的同一句话，却每问一次烧一次模型调用。

### 1.2 跨语言下，检索精度本就有限

语料是英文，用户问的是中文。bge-m3 的**稀疏向量是词元级的，不做跨语言对齐**——中文问题和英文语料之间，token 根本不是同一批，稀疏路基本空转，全靠稠密路撑。

而稠密路的强项是「语义像不像」，不是「是不是这一条」。实测中「IOSS 的适用金额上限」拿 0.5867，「OSS 的申报流程」这类语义很近的问题会挤在同一个分数区间（见 `handoff-2026-09-29.md` 第 5 节的实测分布）。语义接近但答案不同，稠密路分不开。

### 1.3 「是不是问答」本来就是段落级属性

`doc_type` 曾经有一个 `faq` 取值，用来标记「这份材料是问答形式」。这个取值已经拿掉（commit `ae474f8`），理由是：它混了两种互不相干的东西——「官方指南」「法规条文」「平台政策」说的是材料的**权威性与来源性质**，「常见问题」说的是**内容的组织形式**。

更直接的证据是欧盟那份指南里本身就带问答章节（`4.2.10 IOSS Questions and answers`）。同一份文档里既有正文又有问答，说明「是不是问答」是**段落级的属性，不是文档级的**。挂在文档类型上从一开始就不对。

## 2. 决策

**FAQ 作为一份独立的问答表存在，不进入向量库。**

```
用户提问
  ↓
① 拿原问题去 FAQ 问题集里精确比对
  ├─ 命中 → 直出
  └─ 没命中 ↓
② 走 BM25 算分，看有没有超过阈值
  ├─ 没超 → 走原有 RAG 链路
  └─ 超了 ↓
③ 按命中的问题取答案 → 直出
```

问和答本来就是分开的字段，**不需要任何「判定这段是不是一问一答」的环节**。

第 ③ 步**没有**「取不到答案就走 RAG」的兜底，这是有意的，理由见 2.5。

### 2.1 匹配靠关键词，不靠向量

BM25 对**封闭的几十条问题清单**正合适。向量检索的强项是对没见过的表达友好，这个优势在封闭集合里用不上；而它的弱项（语义近但答案不同）在这里恰恰致命，而且分数不可解释——0.62 和 0.65 哪个是「就是这条」，说不清。

BM25 的分数有明确的构成（词频 × IDF），错了好排查。

### 2.2 切词用 jieba，且不配缩写词典

已实测：**jieba 默认把连续英文整段保留**，`IOSS`、`VAT`、`OSS`、`EU`、`DE` 都原样成一个 token，IDF 该有的权重都在。所以原先担心的「`IOSS` 被拆成 `I` `O` `S` `S`、IDF 趋近 0、区分度消失」不会发生，不需要手工补缩写词典。

要留意的是**同义词**：用户问「IOSS 的上限」，FAQ 写「进口一站式服务的适用金额上限」，两边一个词都对不上——BM25 只看字面。

**不专门治它**：没命中就走 RAG（流程第 ② 步的分支），稠密路处理同义本来就是强项。同义词只会让直出覆盖率低一点，不会让用户拿到错答案。

### 2.3 术语在问题里保留原文

问题写成 `进口一站式服务(IOSS)的适用金额上限`。已实测切分干净：

```
进口一站式服务(IOSS)的适用金额上限 → 进口 | 一站式 | 服务 | ( | IOSS | ) | 的 | 适用 | 金额 | 上限
```

本质是**手工版的查询扩展**——正经做法是维护同义词表、检索时把查询扩成「IOSS OR 进口一站式服务」，写死在语料里效果一样，对几十条的人工语料更省事，不用额外一套运行时逻辑。

而且**术语表本来就是翻译要用的同一份**，不是额外负担。

局限说清楚：它治的是术语，治不了整句改写（用户问「最多能卖多少钱」、FAQ 写「适用金额上限」），那类靠 RAG 兜底。

### 2.4 直出也带引用，指向英文原文段落

答案是人工翻的，佐证在英文原文里。不给引用就断了「可追溯」这条线——而那是本项目的核心主张（`00-overview.md` 第 2 节）。

所以每条 FAQ 在建立时就要记下它在原文里的位置（`chunk_id` + 字符偏移，与现有引用同一个形状）。**前提是原文已入库**，否则没有位置可指。三篇语料都在库里，条件满足。

### 2.5 没有「取不到答案就走 RAG」这条分支

早先的流程草案在第 ③ 步写了一个「没拿到答案 → 走 RAG」的兜底。**那是错的，已删除。**

理由：**BM25 的候选集就是 FAQ 表的问题集**，候选集里每一条都来自那张表。所以「分数超过阈值」意味着匹配上了表里的某一行；拿这一行去取答案，除非**该行的答案字段为空**，否则必然取到。

也就是说，那个分支覆盖的**不是**「FAQ 里没有这条」，而是「这条 FAQ 自己缺答案」。这是**数据缺陷，不是检索问题**。

**掩盖它比暴露它危险。** 走 RAG 会让用户拿到一个看似正常的降级结果，而表里那条脏数据没有任何人知道——它会一直留在那里，每次有人问到都静默降级一次。

这与项目一贯的做法一致：`passes_prefilter` 在阈值未标定时宁可报错也不放行，`init_storage.py` 对库里多出来的列只报告不删除、不替人决定。**显式失败优于静默降级。**

所以取不到答案时**报错并留痕**：返回 `internal_error`，日志带上问题与 FAQ 行标识，便于直接定位到那张表的那一行。

### 2.6 数据门禁前移到入库与加载

既然查询路径不再兜底，脏数据就必须在**进入候选集之前**被拦住。两道：

**一、入库门禁。** 问题为空、或答案为空的行**不得入库**。这与 `02-architecture.md` 第 6.2 节的引用溯源门禁、`ingestion/parser/quality.py` 的质量门禁是同一套思路——缺陷拦在入口，不放进来靠下游兜。

**二、加载时过滤。** 问题集加载进内存或写进 Redis 缓存时，再过滤一次并在过滤发生时报警。这一道防的是**历史数据**：门禁是后加的，之前入库的行没经过它。

两道都做，理由是它们拦的不是同一批数据。

### 2.7 Redis 的角色：只是缓存

问题集的**唯一来源是 MySQL 的 FAQ 表**。Redis 里面的问题列表是它的缓存：

- **缓存失效一律回源 MySQL**，不得把 Redis 当成唯一来源。Redis 被清空、过期、或根本没预热时，行为必须与缓存命中时一致，只是多一次回源查询
- 缓存与 MySQL **不一致时以 MySQL 为准**，缓存重建
- 这与查询缓存、会话上下文对 Redis 的定位一致（`03-data-model.md` 第 4 节）

**为什么问题集要缓存**：精确命中与 BM25 算分都在内存里做，缓存的作用是省掉每次启动/回源的一次全表读取，不是提供数据。

## 3. 备选方案与取舍

| 备选 | 否决理由 |
|---|---|
| **把 FAQ 当普通文档入库，用 `doc_type` 筛** | 已实施过，已撤销（`ae474f8`）。`doc_type` 判的是材料权威性而非内容组织形式；且原文里正文与问答同处一篇，「是不是问答」是段落级属性 |
| **用向量匹配 FAQ** | FAQ 是封闭的几十条，向量检索「对没见过的表达友好」这个优势用不上；而它「语义近但答案不同」的弱项在这里致命，且分数不可解释 |
| **不直出，只改进 RAG** | RAG 的召回精度受稠密路本身限制（1.2 节），提高召回解决不了「答案每次都重新生成」这个成本问题 |
| **全人工翻译 vs 机器翻 + 人工抽查** | **未定，见第 5 节** |
| **subword 切词（复用已有的 XLM-RoBERTa tokenizer）** | subword 会把中文切碎，「服务」「服务器」「服务业」的区分度消失，IDF 失效后退化成「谁命中的字多谁赢」。它的强项（对未登录词友好）在封闭问题清单里用不上 |
| **给 jieba 配自定义缩写词典** | 实测不需要（2.2 节），纯大写缩写它认得 |

## 4. 后果

### 4.1 需要跟着改的地方

| 文档或模块 | 改动 |
|---|---|
| `01-scope.md` 第 1.1 节 | 增列这一项能力（**本轮变更流程的落点**，见第 6 节） |
| `03-data-model.md` 第 3 节 | 加一张 FAQ 问答表（问题、答案、指向原文的位置）。**问题与答案两列加非空约束**（2.6 节的门禁落在表结构上） |
| `03-data-model.md` 第 4.2 节 | 加 Redis 键：问题集**缓存**。要写明它是缓存不是来源，失效回源 MySQL（2.7 节） |
| `04-api-contract.md` | 定直出响应的形状。它和 RAG 响应不同（RAG 带命中的子块，直出带指向原文的位置），要定一个能共存的形状；并补上「匹配上了但答案为空」对应的错误码说明 |
| `config/settings.py` | 加 BM25 命中阈值配置项 |
| `services/` | 在调 RAG 之前插一层：先查 FAQ，未命中才走 RAG。取不到答案时报错，**不得降级** |
| `pyproject.toml` | 新增依赖 `jieba` |
| 加载路径 | 问题集加载进内存与写缓存时各过滤一次，发现空答案即报警（2.6 节第二道门禁） |

### 4.2 新增的数据生产工作

**这份问答对现在不存在，要新建。** 首期语料只有 3 篇，FAQ 需要人工从语料里整理出高频问答，再翻译成中文。这是一项独立的工作量，不是写代码能解决的。

### 4.3 风险

**机器翻错了用户看不出来。** 直出的答案有出处、有引用，看着挺像回事。如果翻译有误，用户没有任何线索能察觉。这是这条链路最主要的风险，也是第 5 节那个待定项的由来。

**BM25 阈值同样要标定。** 「分数超过多少算命中」不能拍脑袋——它和语料规模强相关（FAQ 条数变了，IDF 跟着变，分数分布也跟着变）。好处是标定只需要 FAQ 那几十条问题，不用跑端到端，比拒答阈值好标。

**同一条问答会命中两次。** 中文 FAQ 和英文原文同时参与召回时，同一条问答会既以译文命中、又以原文命中。

**门禁是后加的，历史数据要清一遍。** 2.6 节的两道门禁都建立之后才入库的数据才有保障。在此之前如果已经有 FAQ 入库，需要跑一次全量检查、清掉「有问无答」的行——否则那些行会在加载时被过滤，表现为「这条 FAQ 明明在库里却匹配不上」，比直接报错更难查。

**中文 FAQ 解决的不是「跨语言检索」这个整体问题。** 欧盟那份指南里问答只占一部分，剩下大段是正文，中文问题命中正文仍然要靠稠密路，这一点没变。

### 4.4 不做的后果

- 高频问题每问一次烧一次模型调用
- 中文问题继续全靠稠密路单路支撑

## 5. 待定项

以下几条**没有在讨论中定下来**，实现前必须先定：

**一、翻译谁来做。** 机器翻（走百炼）+ 人工抽查，还是全人工？机器翻的成本低，但对应 4.3 节的主要风险；全人工成本高，但可控。两者可以按问题的重要程度分档。

**二、答案里要不要保留原文术语。** 问题里保留是为了匹配（2.3 节），答案里保留是另一回事——中文答案里夹 `(IOSS)` 读着累不累，取决于保留多少。倾向「首次出现保留、后面用中文」，但这是可读性问题，不影响检索效果。

**三、BM25 的 k1 与 b 取值。** 用库的默认值还是调？两者都影响分数分布，而分数分布又决定阈值——要在标定时一并看。
